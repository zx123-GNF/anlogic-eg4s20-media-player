## 1. 为什么要一个新工程（M6 而不是改 M5）

M3 的播放器只有 BMP 一条路：`m3_fat_bmp` 扫根目录、按 `IMGnnnn` 编号排序、逐行把 640×480×24 bit 写进 SDRAM 页。
M5 只有视频一条路：`m5_stream` 直接找**写死的** `VID0.M5V`，`m5_vdec` 解 RLE 后把整帧流进 SDRAM 环形区。

两者的"播放列表"语义完全不同（一个按文件名编号挑图，一个只有单文件），而用户要的是**一个列表里两种条目混排、一套按键/数码管/自动播放规则**。所以 M6 的做法是：

* 保留 M3 的 FAT32 mount + 根目录扫描（它已经能在真实卡上工作），把它升级成**混排列表**；
* 保留 M5 的 RLE 解码器和 HDMI 内嵌音频链路（已验证过声音）；
* 把"谁能用 SD 引擎 + WR1 写口"做成**单一 owner 仲裁**，两个播放引擎互斥运行；
* 删掉 M4/M5 的 WM8960 I²S + I²C 整条支路（这条支路一直是静音的，交付路径是 HDMI 音频），省下 15 个 BRAM 和一批 LUT/时序压力。

## 2. 系统架构

```
                    ┌──────────────── 100 MHz (sdram_clk) ─────────────────┐
 TF 卡 ──SPI 12.5M──►  m6_sd_sec (厂商 sd_card_control + 看门狗)              │
                            │ 512 B 扇区缓冲 (RD_RAM)                        │
             owner=0 ┌──────┴──────────────────────────────┐ owner=1          │
                     ▼                                     ▼                 │
              m6_fat  (播放列表引擎)                 m6_vstream (簇链块流)    │
              · MBR/BPB mount                      · 参数来自 m6_fat         │
              · 根目录扫描 → {key,clus,size}        · 512 B 一块，valid/ready  │
              · key = {is_video, 4 位编号}                 │                  │
              · 选择/排名/按键/自动播放                    ▼                  │
              · BMP 头检查 + 像素流 ──► m6_pix_pump   m6_vdec (M5V1 解码)    │
                     │                       │        · RLE → RGB332→RGB888  │
                     │                       ▼        · ×2 放大 → 307 200 字 │
                     │                  m6_page_wr     · 连续 WR1 环形写      │
                     │                  (逐行 128 字)   · 48 kHz 音频还原     │
                     └──────────┬────────────┴──────────────┬────────────────┘
                                ▼                           ▼
                        Sdram_Control_4Port (WR1 环形 614 400 字 = 2 页 / RD1+RD2)
                                │
                    73.333 MHz  ▼ m6_video_src720：1280×720 光栅 + 640×480 居中窗口
                                │  · 每帧只在窗口内读 1 字/像素，页交换在行消隐
                                │  · 按键去抖/长短按、3.02 s 自动换图、页切换
                                ▼
                   HDMI 1.4b 加密核 (AXIS RGB) ──► TMDS 4 lane ──► 显示器
                                ▲ + 内嵌音频 (LPCM 24 bit + ACR N=6144)
                     m6_aud_fifo (4096 样本) ← 解码器音频 ← 48 kHz 相位累加器
```

**一个 SD 引擎，两个所有者**：`m6_fat` 在 mount/扫描/装图时拥有 SD 引擎、厂商扇区 RAM 读口、WR1 写口和"页完成"脉冲；`m6_vstream` 在放视频时拥有同一批资源。切换点只有一个：`m6_fat` 进入 `S_VID`（拉高 `O_vid_req`）→ `m6_top` 把视频引擎从复位里放出来；视频结束后 `m6_top` 先停引擎（`I_vid_idle`），`m6_fat` 才允许再碰 WR1/SD。

**为什么视频不需要重新 mount**：`m6_fat` 已经解析出 `data_lba / fat_lba / spc / log2spc`，直接把这 4 个数连同"首簇 + 文件长度"交给 `m6_vstream`，后者只做"簇 → 扇区"的算术和簇链遍历，**不再重复 M5 里那套 mount + 目录扫描**（也省掉了每段视频重新初始化 SD 卡的时间）。

## 3. 播放列表与按键语义

### 3.1 名字 → key

| 名字模式 | 类型 | key（17 bit） | 例子 |
|---|---|---|---|
| `IMG<编号>.BMP` | 图片 | `{1'b0, 编号}` | `IMG0001.BMP` → `0x00001` |
| `VID<编号>.M5V` | 视频 | `{1'b1, 编号}` | `VID0005.M5V` → `0x10005` |

编号 1~4 位十进制、其余字节为空格（`0x20`）。所以 `VID0.M5V`（M5 演示片）编号是 0，会排在第 1 段视频。播
放顺序 = key 升序 = **先按编号，同编号图片在视频前**。默认命名（5 图 + 3 视频）自然是"5 张照片、再 3 段视频"，
想改顺序就改文件名编号。

### 3.2 位置（数码管右 4 位）怎么算

列表按目录顺序存放（M3 的做法：不排序，避免 16 路比较器把 100 MHz 打穿），所以**序号不能直接用数组下标**。
M6 维护一个 1 起的位置计数器 `S_rank`：

* "下一个"：`rank+1`；扫描若没找到更大的 key（说明到尾了）→ 回到 1；
* "上一个"：`rank-1`；若已经是最小 key → 变成 `count`。

这样数码管显示的永远等于真实播放顺序里的位置，跟目录顺序无关。

### 3.3 状态机（`m6_fat`，新增状态加粗）

```
S_POR → S_BOOT → S_INIT1/W → S_MBR → S_SIG_C → S_FS_C/S_PENT_C → S_BPB → S_BF1/2_C
      → S_DIR/S_DIR_W/S_ENT/S_ENT_C/S_DIRN → S_DFAT…V     （mount + 根目录扫描，建列表）
      → S_SEL → S_SCAN_W  （选目标：按 key 扫描 + 排名）
      → 图片：S_HDR → S_HF_C → S_DSEC…S_CFAT → S_DEND → S_SW0/S_SW1 → S_SHOW → S_KEY
      → 视频：S_VID（等 I_vid_end / 按键）→ S_VIDW（等引擎停）→ **S_VSET**（25 ms 落定）→ S_SCAN_W
      → S_KEY（等按键/自动播放计时）
```

### 3.4 按键

| 操作 | 行为 |
|---|---|
| `S0`（KEY0）短按 | 下一个（照片立刻换、视频立刻切走） |
| `S1`（KEY1）短按 | 上一个 |
| `S0` 长按 ≥1 s | 暂停/恢复。**暂停 = 只停"自动往下走"**：照片停住；视频照常播（可以长按进入浏览后短按逐项切换，视频也能切到并播放）；视频播完停在最后一帧，不自动进下一项 |
| 自动播放 | 照片每 179 帧（3.02 s）自动换下一项；视频由解码器的帧计数自己判断结束 |

> 关键设计：暂停**不再**冻结字节流（M5 的写法是暂停时把 valid 掐掉）。否则暂停后切到视频，视频永远解不出画面——
> 这正是第一版上板时用户报的"暂停后只能切图片、切不到视频"。现在"停住"由"视频播完不前进（`S_vid_hold`）"实现。

## 4. 两个播放引擎

### 4.1 图片：M3 代码原样搬过来

`m6_fat` 检查 BMP 头（`BM`、biSize=40、640×480、24 bit、压缩 0），`m6_pix_pump` 把扇区里的 BGR 像素转成 24 bit，
`m6_page_wr` 每行 128 字突发写进**当前没显示的那一页**，写完整页后发"页完成"脉冲，显示模块在下一个行消隐把页换过来。
搬运过程上一页继续显示，所以看不到中间过程（只有换页瞬间的干净切换）。

### 4.2 视频：M5 解码器 + 新的块流器

`m6_vdec` 与 M5 相同（RGB332 RLE → ×2 放大 → 307 200 字/帧），只加了三处：

| 改动 | 原因 |
|---|---|
| `I_start_page`：帧 0 写到"当前没显示"的那一页 | 从照片切到视频时，第一帧落在隐藏页，换页时一次到位，**不会撕裂/刷屏** |
| `O_pg_done/O_pg_page` 改成脉冲 + 页号 | 图片和视频共用一个"页完成"翻转器（在 `m6_top`），避免 mux 两个翻转信号在 owner 切换瞬间产生假沿 |
| `O_clip_end` 脉冲 + 帧数/音频字节改**递减计数器** | 播列表靠它进下一项；递减计数器把 `+1 >= 帧数` 的 16 bit 加法器+比较器（10.26 ns，SWNS −0.543 ns 的元凶）换成 `== 1` 的宽与门 |

`m6_vstream` 是**新写的紧凑块流器**（M5 的 mount + 目录扫描整段删掉，只留"给定首簇和长度，把文件当字节流吐出来"）：
每 512 B 一个扇区读 → 拷进本地双口 RAM → 按 valid/ready 一字节一字节交出去；簇用完就查 FAT 拿下一簇；
字节数到文件长度就回卷（解码器用文件头里的帧数自己判断结束）。参数由 `m6_fat` 给：`clus / size / data_lba / fat_lba / spc / log2spc`。

## 5. 上板踩到的三个真 bug（每个都由 UART 快照定位）

调试手段：`m6_dbg_vid` 每 0.5 s 打一行固定宽度十六进制，**并且在每段视频结束时把当时的内部状态锁存**再打印
（"视频只播 0.1 s 就没了"这种故障，0.5 s 轮询根本抓不到）。一行内容：

```
V<sst> <vst> <err> <mnt> <frm> <vbyt> <vpx> <audn> <len> <byt> <chk> <first> <lba> <size> <eof>
```

### 5.1 簇链取数早一拍 → 视频只播第一个簇（最关键的 bug）

**现象**：视频出来第一帧（对的），然后画面被下一张照片从下往上刷掉，没有声音；串口快照
`err=4 frm=0001 vbyt=0x0000B9FD byt=0x0000B9FD len=0`——解码器正好消费了一帧的字节（8+41165+6400+32），
然后读到的"下一帧块头"是 0。

**根因**：`m6_vstream` 里读 FAT 表项的 4 字节取数引擎少等了一拍。本地扇区缓冲是**寄存器输出**的读口
（地址 → 下一拍数据），我写的状态机在"设地址"的下一拍就取数据 → 取到上一次的旧地址数据 → FAT 返回的下一簇全是错的，
第一簇之后跳到随机簇（那里是空白区，全 0）。

**修复**：改用 M5 里已经验证过的四状态取数引擎（`F_IDLE` 设地址 → `F_RD` 等一拍 → `F_CNT` 取字节 → `F_CAP` 移位并设下一地址）。

**证据**：修好后串口立刻显示 `vbyt = 0x016F2097 = 24 060 055`（正好等于文件长度），`frm` 归零、`err=0`、`rsn=1`（正常播完）。

### 5.2 列表扫描漏掉最后一个条目 → 序号乱跳、最后一段视频永远播不到

**现象**：数码管总条数 07，但右边序号能涨到十几；最后一段视频从来不播。

**根因**：M3 的 min/max 扫描在"最后一个条目"那一拍，用的是**寄存器里旧的候选标志**来决定结果
（`C_idx <= C_have_gt ? ...`），所以最后一个数组元素永远没机会成为"下一个"。而列表是目录顺序，最后一段视频
恰好排在最后 → 它永远不会被选中，"下一个"退化成"回到第一个"，位置计数器也就跟真实顺序脱节。

**修复**：把"当前条目是否更优"做成组合逻辑（`W_gt_hit/W_all_hit`），最后一拍用 `C_have_gt | W_gt_hit` 参与决策。

**证据**：修好后串口 `key=0x10006`（最后一段视频）、`rank=7`、`选过 7 次`——正好等于 5 图 + 2 视频的条数。

### 5.3 RLE 像素计数器 12 bit → 4096 绕回 0

**根因**：token 的 count 字段是"像素数−1"，最大 4096；M5 的解码器用 `reg [11:0] S_left` 存像素数，
4096 直接截成 0 → 每个 4096 的 token 少写 1 个像素（literal token 还少消费 1 字节 → RLE 流错位、画面被斜切）。
M5 的演示片没撞上，真实影片大片平坦区很容易出现 4096 的 run。

**修复**：`S_left` 加宽到 13 bit，比较常量同步改成 `13'd1`。

### 5.4 顺带修掉的两个"半 bug"

* **切视频/切图片的页选择用到了还没落定的 `S_disp_page`**：视频最后一帧的换页要等到下一个行消隐才生效，
  而 `m6_fat` 立刻按 `~S_disp_sync` 选目标页 → 选到了"马上要显示"的那一页 → 新照片被从下往上刷在视频画面上。
  修复：视频结束后加 **25 ms 落定等待（`S_VSET`）**，再选页。
* **100 MHz 时序违例 −0.543 ns**：`(O_frame_cnt + 1) >= S_frames`（16 bit 加法 + 16 bit 有符号比较，11 级逻辑，10.263 ns）
  直接压在帧边界判断上。改成递减计数 `S_fr_left == 1` 后回到 **+0.102 ns**。

  > 这个违例很可能就是用户看到的"视频右边一长条被挪到左边"：帧边界逻辑在临界路径上，一旦打偏，帧写指针就错位，
  > 表现在画面上就是整幅画面横向错位。改成递减计数后该现象消失（用户复测确认）。

## 6. 片源：`tools/m6_encode.py`

M5 的 `m5_encode.py` 固定 RGB332、无质量自适应，实测**真实影片**一帧要 47 kB → 47 kB × 15 fps = 705 kB/s，
超过 TF 卡带宽。`m6_encode.py` 在此之上加了**逐帧字节预算**：

| 档位 | 处理 | 用途 |
|---|---|---|
| `rgb332` | 原样 | 平滑/静态帧（大多数） |
| `q4` | 每通道 4 级量化 | 细节多、RLE 压不下来 |
| `medq4` | 3×3 中值 + 4 级量化 | 噪声大（颗粒/纹理） |
| `q2` | 每通道 2 级量化 | 兜底 |

每帧从 `rgb332` 开始试，超预算就降一档，直到 ≤ `--max-kb`（默认 36 kB）。

实测（两段微信视频，1280×720 30 fps 源 → 320×240 15 fps）：

| 文件 | 帧数 | 时长 | 大小 | 平均负载 | 峰值负载 | 需求带宽 |
|---|---|---|---|---|---|---|
| `VID0005.M5V` | 579 | 38.6 s | 19.7 MB | 28.7 kB | 36.0 kB | 524 kB/s |
| `VID0006.M5V` | 371 | 24.7 s | 13.0 MB | 29.5 kB | 36.0 kB | 536 kB/s |

自适应档位命中率：`rgb332` 约 51 %、`q4` 约 33 %、`medq4` 约 16 %、`q2` 1 %。

用法：

```powershell
$py = "C:\Users\31860\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\python\python.exe"
& $py tools\m6_encode.py 输入.mp4 out --name VID0007.M5V --max-kb 36
# 输出到 out\VID0007.M5V，拷到 TF 卡根目录（名字必须符合 VID<1~4 位数字>.M5V）
```

离线检查工具：`tools/measure_m5_bitrate.py` 只统计"如果按这个码率编，链路够不够"，
可以先用几帧估一下再决定 `--max-kb` / `--fps`。

## 7. 带宽账（为什么把 SPI 从 5 MHz 提到 12.5 MHz）

| 项 | 数值 | 备注 |
|---|---|---|
| 扇区读时间 @5 MHz | 820 µs | M5 实测值 |
| 扇区读时间 @12.5 MHz | ~330 µs | 按比例，实测 12.5 MHz 全链路工作正常 |
| 视频需求（含 FAT 遍历 ~12 %） | 536 kB/s @15 fps | 见 §6 |
| 照片加载 | 0.9 MB/张 | @12.5 MHz 约 0.6 s（M3 的 5 MHz 是 1.5 s） |
| M5 版 5 MHz 的实测有效带宽 | 约 390 kB/s 就能稳定播 | 所以 5 MHz 上限约 0.6 MB/s |
| M6 12.5 MHz | 约 1.0~1.1 MB/s | 视频占 ~50 %，峰值帧 ~70 % |

> 5 MHz 也能播（第一版就是），但遇到细节多的片段（一帧 50 kB）就会追不上而"一卡一卡"；
> 12.5 MHz + 36 kB 预算之后余量足够，用户复测不再卡。

| 4 | 视频 | 画面流畅、有声音、播完自动进下一段 | ✅ |
| 5 | `S0` 短按 / `S1` 短按 | 下一条 / 上一条（图片和视频都能切） | ✅ |
| 6 | `S0` 长按 1 s | 暂停（两端小数点点亮）；再次长按恢复 | ✅ |
| 7 | 暂停后短按 `S0`/`S1` | 能切到视频并播放；视频播完停住等按键 | ✅ |
| 8 | 串口快照 | 每段视频结束 `err=0 / rsn=1 / vbyt=文件长度` | ✅（两段都验证） |
| 9 | 画面几何 | 无横向错位/条纹 | ✅（修掉 −0.543 ns 违例后） |

## 9. 已知问题 / 后续可做

1. **暂停时切到视频会从第一帧开始播**（不是"继续上次位置"）。当前语义是"选择即播放"，够用；若要做"逐帧浏览"需要给解码器加单帧步进。
2. **照片加载（约 0.6 s）期间按键只排队不打断**（M3 的既有行为，最多同时排队 3 个）。
3. **视频播完到下一项之间有约 25 ms 落定 + 一帧首帧延迟**（换来的是不撕裂），切项时会有一次极短的画面停留。
4. **视频文件名必须 `VID` 前缀 + 1~4 位数字 + `.M5V` 扩展名**；不符合的条目会被忽略（旧的 `VID0.M5V` 现在能识别，因为允许 1 位数字）。
5. **列表上限 16 条**（`MAXF`），超过的条目不进列表。
6. **WM8960/ES8388 耳机口仍然是静音的**（M4 遗留问题，未在 M6 接回来）；交付的声音路径是 HDMI 内嵌音频。
7. **SPI 时钟只在 5/10/12.5/25 MHz 这几档**（分频器限制）；换卡后若 12.5 MHz 不稳定，改 `rtl/m6_sd_sec.v` 一行回 10 MHz 即可（片源不用重编，只是余量变小）。

## 11. 与 M5 的差异一览

| 项 | M5 | M6 |
|---|---|---|
| 片源 | 单个写死 `VID0.M5V` | 根目录任意 `IMGnnnn.BMP` + `VIDnnnn.M5V` 混排 |
| 列表/顺序 | 无 | key = {类型, 编号}，自动 next/prev/循环 |
| 照片 | 无（只有 640×480 BMP 的历史工程） | M3 的 BMP 通路原样保留，与视频共用一个播放列表 |
| 数码管 | 显示帧号（用户反馈"乱码/地址"） | 总条数 + 当前第几条 |
| TF 卡时钟 | 5 MHz | 12.5 MHz |
| 声音 | HDMI 内嵌音频 + 一条静音的 I²S 支路 | 只保留 HDMI 内嵌音频（省 15 BRAM） |
| 码率控制 | 固定 RGB332 | 逐帧预算 + 4 档自适应量化 |
| 每段视频启动 | 单文件、无需切换 | owner 仲裁 + `I_start_page` 防撕裂 + 25 ms 落定 |
| 资源 | LUT 5 363 / BRAM 48 | LUT 7 700 / BRAM 33 |
| 时序 | SWNS +0.225 / +0.138 | SWNS +0.102 |
| 固化 | SRAM | SPI 配置 Flash（断电自启动） |
