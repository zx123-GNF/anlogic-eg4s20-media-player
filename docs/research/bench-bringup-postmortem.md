# 上板调试复盘：一层层剥开的 7 个 bug

> 记录 2026-10-22 晚上把「TF 卡 BMP 播放器」从「黑屏」调到「正常出图」的全过程
> （§2 的 bug ①–⑤），以及 2026-10-23 晚上把 M4 音频从「没声音」调到「1 kHz 出声」（§6 的 bug ⑥⑦）。
> 这份文档可以直接用作设计报告的「调试过程 / 问题分析」章节，也可以当团队的踩坑手册。
>
> 结论先行：**屏幕上一个"黑屏"，背后叠了 5 个互相独立的故障**，其中 2 个是厂商例程自带的缺陷，
> 2 个是我自己在改造/移植时引入的，1 个是显示器本身的行为。任何一个没修，现象都是"不出图"。
> 音频的"没声音"背后是 2 个故障：1 个是我们自己 I²C 状态机的字节间时序，1 个是引脚接反
> （管脚表写错，以核心板原理图为准）。

## 1. 症状时间线（为什么会绕远路）

| 观察到的现象 | 当时的误判 | 真实原因 |
|---|---|---|
| 屏显 "no signal"，但 FPGA 明显在跑（LED 有状态） | 以为 PLL/TMDS 坏了 | 显示器在 FPGA 重配置后**不会自己重锁**，要拔插 HDMI |
| 拔插 HDMI 后彩条正常，但播放器全黑 | 以为 FAT/SD 没工作 | 页写入器**死锁**（bug ②），同时卡也确实没读出来 |
| LED 显示「卡未挂载 + 正在写 + 有错误」，一直不变 | 以为卡接触不良 | 页写入器死锁 + 读卡链路 3 个 bug |
| 数码管/串口都没有 → 只能靠 4 个 LED | —— | 缺可观测性，于是先补了 UART 调试通道 |

> 教训 1：**"黑屏"不是一种故障，是一类现象**。先花 10 分钟把可观测性做出来（串口打印），
> 比对着屏幕猜半小时有效得多。

## 2. 五个 bug

### bug ①：显示器丢锁 —— 不是设计问题

- **现象**：烧完新 bit 后屏显 `no signal`；**同一个 bit**，把 HDMI 线拔下再插上就正常出图。
- **原因**：FPGA 重配置时 TMDS 会中断约 1 秒。这块便携屏丢锁后**不会自动重新握手**（板上也没有
  HPD/DDC，FPGA 无法主动通知屏）。
- **验证/修复**：A/B 对照实验 —— 同一 bit，拔插前 no signal、拔插后正常。**不需要改 RTL**。
- **固化到流程**：`tools/flash.ps1` 之后必须拔插一次 HDMI；写进 `docs/board-test-guide.md`。

### bug ②：页写入器死锁 —— 720p 改造时参数传错

- **现象**：全黑；`led` 长期显示 `busy=1`（正在写永不结束），页号不翻转。
- **原因**：`m2_page_wr` 的 `HACTIVE/VACTIVE` 描述的是**一页帧缓冲的几何**（640×480 = 307200 字，
  行宽 640、行数 480，行地址硬编码 `row*640`）。720p 改造时我把**画布尺寸** 1280×720 传了进去：
  - 写入器以为要收 `1280*720 = 921600` 个像素才 `done`；
  - 而 BMP 装载器/测试图案只产生 **307200** 个像素；
  - 没卡时走测试图案：图案发完在 `S_PAT_E` 等 `I_wr_done`，写入器在 `W_ROW` 等像素 → **双向死锁**。
- **修复**：给 `m2_page_wr` 传 `PAGE_W/PAGE_H = 640/480`；画布尺寸只给视频源和 HDMI core。
- **教训**：多坐标系（画布 / 窗口 / 帧缓冲 / 扇区）必须各自命名清楚，**不要共用一个 `HACTIVE`**。

### bug ③：`m2_byte_seq` 字节整体错位一格 —— RAM 读延迟

- **现象**：SD 卡流程"全部成功"，但读回的 MBR 签名是 `55 55`，应为 `55 AA`；分区类型读成 `0x00`，应为 `0x0C`。
- **原因**：扇区缓冲 RAM（`ram_dual_port_simple`）的读口是 `doutb <= ram[addrb]`，即
  **第 t 拍看到的数据是第 t-1 拍给的地址对应的数据**。`m2_byte_seq` 在 `S_PRE` 那一拍没有递增地址：

  ```
  期望: V[0]=mem[510]=0x55, V[1]=mem[511]=0xAA
  实际: V[0]=mem[510]=0x55, V[1]=mem[510]=0x55   ← 重复，后面全部滞后一格
  ```

- **怎么抓到的**：UART 调试通道把每次字节读取的 `偏移/长度/状态/34 个原始字节` 打出来，一眼看到 `55 55`。
- **修复**：`S_PRE` 里也 `O_addr <= O_addr + 1`（第 1 个字节仍然正确，后续字节对齐）。
- **教训**：**凡是有 RAM 的地方都要问"数据是第几拍有效的"**。这类"流程全对、数据全错"的 bug 在仿真里
  几乎看不出来，除非专门盯 RAM 延迟。

### bug ④：厂商 SD 引擎的字节计数器不随 `start` 复位

- **现象**：第 1 个扇区（MBR）读得完全正确；第 2 个扇区（BPB）起数据是乱的（`80 00 22 04…`，应为 `00 02 20 4A…`）。
- **原因**：`sd_read_data` 内部 `cnt`（写缓冲区的字节地址计数器）**只被 `rst` 清零，不被 `start` 清零**。
  第一次读结束后计数器停在 514，第二次读就从 0 附近继续绕 → 字节写到错误地址。
  该例程原本只演示"按一次读一个扇区"，所以缺陷没暴露。
- **修复**：在 `m2_sd_sec` 里**每次事务开始前把 SD 引擎复位 8 拍**（`S_RST` 状态），使计数器归零。
- **验证**：UART 打出的 BPB 字段变成 `BPS=512 / 簇=32 扇区 / 保留=3146 / FAT 数=2`，FATSz32=14811、RootClus=2，
  与 PC 上读到的分区信息完全一致。
- **教训**：**厂商例程 ≠ 正确代码**，尤其"只跑过一次"的演示工程。

### bug ⑤：BPB 检查把两次读取的字段混用 + 偏移写错

- **现象**：`err=2`（FAT32 BPB 检查失败），换哪张卡都失败。
- **原因**（两个独立错误）：
  1. `B[]` 只是**一块 34 字节的窗口**（`m2_byte_seq` 的输出）。BPB 检查同时用了 offset 11（BPS/簇/保留/FAT 数）
     和 offset 32（FATSz32/RootClus）两次读取的字段，但检查发生时窗口里**只剩第二次**的数据 →
     BPS/簇/保留/FAT 数全是在拿 offset 32 的字节算，必然不成立。
  2. `W_fatsz16` 的注释写"offset 32,33"，实际 offset 32 是 `TotSec32`；于是"FATSz16 必须为 0"这个检查
     变成了"总扇区数低 16 位必须为 0" —— 任何真实卡都不可能通过。
- **修复**：在 `S_BF1_C`（read#1 刚完成、窗口里还是它的数据）把四个字段**锁存**进
  `Q_bps/Q_spc/Q_rsvd/Q_nfat`，检查改用锁存值；删掉错误的 FATSz16 检查（`FATSz32 != 0` + `RootClus >= 2`
  已经足以识别 FAT32）。
- **定位手段**：把 6 个检查条件合成一个 bitmap 打到串口，读出 `0x16` = 只有 read#2 的 3 条通过 →
  立刻定位到"窗口数据被覆盖"。
- **教训**：**跨多次读取的字段必须锁存**；注释和实际偏移必须对齐（最好用 `localparam` 写偏移）。

## 3. 关键工具：UART 调试通道

没有它，上述 ③④⑤ 只能靠猜。做法（`rtl/m2_dbg_uart.v`）：

- 抓取**前 8 次** `byte_seq` 读取：`偏移(9b)`、`长度(6b)`、`FSM 状态(6b)`、`34 个原始字节`；
- 再加一条**实时记录**（当前 FSM 状态 + 错误码 + 检查 bitmap）；
- 每 0.6 s 重发一遍，PC 端随时能读，不依赖复位时机；
- 115200 8N1，PC 端 `tools/read_uart.ps1` 解码。

输出示例（每行一条记录）：

```
A off=510 cnt=2  55 AA                                   MBR 签名 ✓
C off=446 cnt=16 80 2021 00 | 0C | FEFFFF | 00080000 | FF279E03   类型 0x0C、LBA 2048 ✓
D off=11  cnt=7  00 02 | 20 | 4A 0C | 02 | 00             BPS=512、簇=32、保留=3146、FAT=2 ✓
E off=32  cnt=16 FF279E03 | DB390000 | 0000 | 0000 | 02000000    FATSz32=14811、RootClus=2 ✓
Z err=0 state=0x2A (S_KEY)                                显示完成、等按键 ✓
```

实现上踩了两个坑，都记下来了：

| 坑 | 现象 | 解决 |
|---|---|---|
| 用 304 字节数组 + for 循环写快照 | TD 综合成巨型多路器，100 MHz 域 **SWNS −5.2 ns / STNS −374 ns** | 改成 4 个扁平 293 bit 寄存器 |
| 字符生成一条组合链（索引→字节→十六进制） | 单条路径 11.5 ns，**SWNS −1.4 ns** | 拆成 3 级流水寄存器（UART 一位 868 拍，多两拍无所谓） |

另外 `DEBUG_ERR` 参数可以把 3 bit 错误码直接映射到 4 个 LED（亮的灯=二进制位=1），
用于"没有串口时"的粗定位。

## 5. 复盘：下次怎么更快

1. **先做可观测性，再做功能**。上板第一件事是把内部状态吐出来（串口 / 状态寄存器 / 屏上叠加），
   而不是靠 3 个 LED 猜。本次 UART 花了约 40 分钟，直接省掉了后面几小时的试错。
2. **同一现象先做 A/B 对照**（换回已知能跑的 bit、拔插线缆、换卡），把"环境问题"和"设计问题"切开。
3. **厂商代码要当"参考实现"看，不要当"正确实现"**：本次 2/5 的 bug 来自厂商例程（计数器不复位、
   状态机没有超时），1 个来自我自己的参数/移植错误。
4. **坐标系、时钟域、RAM 延迟这三类问题，用命名和注释强制区分**：
   `PAGE_W` vs `HACTIVE`、`Q_bps`（锁存值）vs `W_bps`（当前窗口值）。
5. **每个修复都写清"现象→原因→证据→修法"**（就是本文档的格式），比赛报告直接可用，队友也能接力。

## 6. M4 音频：从「有 POP 声没音乐」到「1 kHz 出声」（2026-10-23 夜）

现场：M4 上板后耳机只有上电 POP 声，LED 显示 **D3（音频 PLL 锁）+ D1（I²C NACK）**，
串口显示视频/FAT 通路正常（`Z err=0 state=0x2A`）。也就是说：播放器本身好的，只有 codec 配不上。

### 6.1 第一步不是改代码，是搞清楚「谁在总线上」

新增 **`rtl/m4_i2c_scan.v`**（`DEBUG_AUDIO == 2`）：复位 50 ms 后，用 40 kHz 单字节写事务
扫 128 个 7 位地址，结果以 ASCII 打到 CH340E（`#SDA=1` + 每个地址一行 `#addr:ack`），
每 ~0.67 s 重复一遍，PC 端不用卡着重启时机。实测：

```
#SDA=1
ACK: 1A  50  51  58
```

| 地址 | 器件 | 结论 |
|---|---|---|
| 0x1A | **WM8960**（7 bit；8 bit 写地址 0x34） | **板上 codec 就是 WM8960** |
| 0x50 | 24LC256 EEPROM | 总线正常 |
| 0x51 | PCF8563 RTC | 总线正常 |
| 0x58 | MAC 地址 EEPROM | 总线正常 |

两个重要推论：
1. **总线、上拉、FPGA 的 I²C 主机、引脚 L16/M16 全都正常**，而且 codec 就在 0x1A。
   之前怀疑「板上是 ES8388（0x20）」是错的——厂商文件夹里那份 ES8388 原理图属于
   **另一个 AC201 版本**，本板是 WM8960 版（与厂商文件夹名一致）。
2. 那么"0x34 也 NACK"就只能是**帧时序**问题，而不是地址问题。

### 6.2 bug ⑥：多字节 I²C 帧，字节之间多出一个 SCL 脉冲

**现象**：单字节探测（扫描器）通通 ACK 正常；3 字节寄存器写（初始化）通通 NACK。

**原因**：WM8960 的一个寄存器写是**一帧 3 字节**（器件地址、reg+data[8]、data[7:0]）。
我们的 bit 引擎在每写完一个字节（含 ACK）后回到 idle 分支，而 idle 分支**无条件把 SCL 拉高**。
可是 ACK 结束时 SCL 本来就是低——于是从机在字节之间看到一个**多余的上升沿**（此时 SDA 已释放 = 高），
把它当成一位数据，第 2、3 个字节整体错一位 → NACK。扫描器每次都只发 1 个字节，所以它没事。

**证据链**：同一套 bit 引擎 + 同样的引脚，单字节事务 ACK、多字节事务 NACK；
且故障点可定位到 `m4_i2s_bit_shift.v` 的字节结束分支（ACK 后 SCL=0 → idle 强制 SCL=1）。

**修法**：新增 `S_hold` 标志。非最后一字节结束时进入 hold：**SCL 保持低、SDA 释放**，
等下一个字节命令到来时直接在 SCL 低电平期间放好数据位；只有 STOP（或异常中止）之后才回空闲高。

**结果**：D3+D2 常亮、D1 熄灭（13 条寄存器全部 ACK），复位后约 **0.55 s**（POR 10 ms + 13 条写 +
VMID 500 ms 等延时）1 kHz 正弦开始出声。

### 6.3 bug ⑦：I²S 引脚接反，还把 codec 的输出脚当输出驱动

修好 ⑥ 之前先查了一遍引脚，发现**管脚表与核心板原理图冲突**：

| FPGA 球 | 核心板 pin | 核心板网络 | 实际含义 | 原设计 | 修正 |
|---|---|---|---|---|---|
| B8 | 96 | ES_MCLK | codec MCLK | 对 | — |
| C8 | 97 | ES_DSCLK | codec SCLK（BCLK） | 对 | — |
| A8 | 98 | ES_DSDIN | **DAC 数据** | 当 DACLRC | **改 DACDAT** |
| A7 | 101 | ES_DLCLK | **LRCK** | 当 DACDAT | **改 DACLRC** |
| C7 | 102 | ES_ASDOUT | **codec 输出（ADCDAT）** | 当 ADCLRC 驱动 | **删除该输出** |

管脚表写的是 `A8=DACLRC / A7=DACDAT / C7=ADCLRC`（按 WM8960 引脚名排的），
但 AC601 核心板原理图（U1 球号→网络）和厂商可运行的 `board_test` 工程 `IO.adc`
（`A8=I2S_DO`、`A7=I2S_RCLK`、`C7=I2S_DI`）都指向 **A8=数据、A7=时钟**。
以核心板原理图为准：LRCK→A7、DACDAT→A8；C7 是 codec 的**输出**脚，
原来拿它当 ADCLRC 推挽输出，等于和 codec 对顶（这次一并删掉，播放路径不需要 ADC）。

### 6.4 验证状态

- 上板：D3（PLL 锁）+ D2（初始化 OK）常亮、D1（NACK）灭；耳机 **1 kHz 出声**。
- 视频/FAT/HDMI 通路未受影响：`tools/read_uart.ps1` 仍显示 `A..H` 快照与 `Z err=0 state=0x2A`。
- 资源/时序：bit **630 799 B**，SWNS **+0.133 ns**（final/routed），5 个时钟域全部收敛。
- `DEBUG_AUDIO`：0 = 正常播放状态灯（发布版），1 = 音频状态灯（D0 busy / D1 NACK / D2 OK / D3 PLL），
  2 = I²C 总线扫描器（串口 ASCII）。发布前必须回到 0。

### 6.5 这次的教训

1. **总线类问题先做"全地址扫描"**：一个 50 行的扫描器 + ASCII 串口，5 分钟就能把
   「从机不在 / 地址错 / 时序错 / 总线坏」分开，比反复改寄存器表有效得多。
2. **"每字节回空闲"的 I²C 状态机，必须检查字节间电平**：ACK 之后 SCL 必须保持低，
   只有 STOP 之后才允许空闲高。单字节测试通过 ≠ 多字节帧正确。
3. **原理图 / 管脚表 / 厂商例程三者冲突时**：先看核心板（唯一的物理实现），
   再用能跑通的厂商例程的 `IO.adc` 交叉验证；三者里只有管脚表这次是错的。
4. **设备地址靠测量确定**：同一块板不同版本的 codec 可能不同（ES8388 vs WM8960），
   地址表不能从文件夹名字推断。
